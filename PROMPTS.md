# Skyline — промпты для Claude Code, Фазы 0 и 1

Каждый блок — **одна сессия, один PR**. Копировать целиком, включая критерии приёмки.

Перед первой сессией репозиторий должен выглядеть так:

```
skyline/
  CLAUDE.md                        ← конвенции проекта, читается автоматически
  docs/
    SPEC.md                        ← полное ТЗ
    prototypes/
      spike-terrain.html           ← проверка рельефа и подложки
      spike-visuals.html           ← сравнение поставщиков, стилей, отрисовки
      prototype-viewer.html        ← рабочий прототип просмотрщика
  fixtures/                        ← из архива: 12 .igc + expected.json + README.md
  tools/
    make-fixtures.mjs
```

Три HTML-файла в `docs/prototypes/` — не код продукта, а рабочие макеты.
На них ссылаются задачи 1.6 и 1.7, и на `spike-visuals.html` завязана
проверка выбора подложки из §4.4.1. Открываются через локальный сервер
(`npx serve docs/prototypes`), не двойным кликом.

Нужны: Node 22, pnpm, Docker, Claude Code.

> **Правило, которое стоит держать в голове всю дорогу:** если Claude Code
> предлагает сделать заодно что-то не из текущей задачи — отказывайся.
> Смешанные PR здесь ломаются чаще всего, потому что задачи связаны данными:
> ошибка в парсере проявится в аналитике, и ты будешь искать её не там.

## Фаза 1 — от файла до 3D

### Сессия 1.1 — парсер IGC ⭐ ключевая задача

```
Прочитай docs/SPEC.md §3.3 и §3.4, затем fixtures/README.md.

Сначала тесты, потом реализация.

Тесты: packages/parsing/src/igc.test.ts.
Источник эталона — fixtures/expected.json: для каждого файла там указаны
pointCount, altitudeSource, invalidFixCount, minWarnings, медианный и
максимальный интервал между фиксами, и три контрольные точки (first, middle,
last) с точными lat/lon/altBaro/altGnss/valid. Координаты посчитаны обратным
декодированием того, что реально лежит в файле, поэтому сверяй на точное
равенство с допуском 1e-9, а не «примерно».

Затем реализуй parseIgc() в packages/parsing/src/igc.ts.

На что обратить особое внимание:
  - Позиции байтов B-записи (1-based): B=1, время 2-7, широта 8-15 (8 символов,
    DDMMmmm + N/S), долгота 16-24 (9 символов, DDDMMmmm + E/W), валидность 25,
    баровысота 26-30, GNSS-высота 31-35, расширения с 36.
    Частая ошибка — отвести широте 7 символов, забыв букву полушария; тогда
    вся долгота читается со сдвигом. Файл baseline.igc это поймает.
  - Оба формата даты: HFDTE150726 и HFDTEDATE:150726,01. Санити-чек: дата
    не в будущем и не раньше 1990.
  - Переход через полночь UTC: время следующей записи меньше предыдущей → +сутки.
  - Расширения LAD и LOD дают дополнительные знаки минут — без них координаты
    огрубляются до ~1.85 м.
  - Отрицательные высоты в формате -NNNN.
  - Парсер НИКОГДА не бросает исключение на кривой строке: пропускает,
    пишет в warnings, продолжает. Пустая строка предупреждения не заслуживает,
    неизвестный тип записи — заслуживает.
  - Функция чистая: на входе строка или Buffer, на выходе ParsedTrack.
    Ни сети, ни файловой системы.

Тип ParsedTrack объяви в packages/core — им будут пользоваться все парсеры.

Критерии приёмки:
  - все 12 файлов из fixtures/ парсятся, значения совпадают с expected.json
  - broken-lines.igc не роняет парсер и даёт ровно столько валидных точек,
    сколько указано в эталоне
  - нет магических чисел: пороги в packages/core/constants.ts с комментариями
  - нет any в экспортируемых сигнатурах
```

### Сессия 1.3 — чистка и производные величины

```
Прочитай docs/SPEC.md §5.2, шаги 3-4, и §6.1.

Реализуй в packages/analysis чистыми функциями (ни сети, ни БД, ни файлов —

  - медианный фильтр по координатам, окно 3
  - отбрасывание фиксов с fxa > 50 м или siu < 4, если поля есть
  - ресэмплинг на равномерную сетку 1 Гц линейной интерполяцией

Разрывы длиннее 30 секунд помечаются флагом gap, интерполяция через них
запрещена. fixtures/gaps.igc содержит разрывы 90 с и 12 мин.

Критерии приёмки:
  - на baseline.igc вертикальная скорость в спирали положительна,
    на переходе отрицательна
  - sparse-10s.igc получает analysis_level = 'basic'
  - gaps.igc: точки по краям разрывов помечены, интерполированных точек
    внутри разрывов нет
```

### Сессия 1.4 — бинарный формат .track

```
Прочитай docs/SPEC.md §5.4 целиком.

Реализуй packages/track-format: writeTrack(points) и readTrack(buffer).
Одна реализация — ею пользуются и apps/worker, и apps/web.

Три вещи, на которых эта задача обычно ломается:
  1. Каждая колонка выравнивается по 8 байт. Без этого
     new Int32Array(buffer, offset, n) бросит RangeError при нечётном
     pointCount — и это всплывёт только на конкретных треках.
     Тест на нечётном количестве точек обязателен.
  2. dt — Uint16 в миллисекундах, потолок 65 535 мс. Разрыв больше
     кодируется как 0xFFFF, фактическая длительность идёт в таблицу
     разрывов в хвосте файла. fixtures/gaps.igc это проверит.
  3. Координаты — delta-of-delta, а не абсолютное смещение от origin.

Критерии приёмки:
  - round-trip на всех фикстурах, включая нечётный pointCount
  - размер выхода на 15 000 точек укладывается в 315 КБ ± 5%
  - readTrack возвращает типизированные массивы, без промежуточных объектов
```

### Сессия 1.5 — загрузка и конвейер

```
Прочитай docs/SPEC.md §5.2, §5.3, §10.

Реализуй:
  - apps/api: POST /api/v1/flights/upload (multipart) — кладёт сырой файл
    в S3/MinIO в gzip, создаёт строку в flights со статусом pending,
    возвращает flightId. Плюс GET /{id}/status, SSE /{id}/events,
    GET /{id}/track
  - apps/worker: внутрипроцессная очередь, пул worker_threads,
    конвейер parse → clean → derive → pack, обновление статусов

КРИТИЧНО — это главный риск стека. Все шаги конвейера исполняются
в worker_threads, а не в основном потоке. Основной поток воркера только
раздаёт задания и пишет статусы. 15 секунд синхронного счёта в основном
потоке остановят и очередь, и SSE.

Плюс восстановительный проход при старте: выбрать из flights всё со статусом
pending или parsing и поставить заново. Без этого файл, загруженный перед
перезапуском, навсегда зависнет.

Ограничения: файл больше 50 МБ или 500 000 точек отклоняется с понятным
сообщением. Ответы — через Zod-схемы из core, ошибки — Problem Details.

Критерии приёмки:
  - curl с baseline.igc возвращает flightId, через несколько секунд
    статус становится ready, .track скачивается и читается readTrack
  - ВО ВРЕМЯ обработки 4-часового трека GET /api/v1/health отвечает
    быстрее 200 мс — это тест, а не ручная проверка
  - перезапуск воркера в середине обработки не теряет полёт
  - битый файл даёт статус failed с кодом ошибки, а не 500
  - замерь и запиши в docs/SPEC.md §5.2 реальное время конвейера
    на baseline.igc — там сейчас стоит прикидочная оценка
```

## Что делать, когда что-то пошло не так

**Тест на фикстуре падает.** Сначала проверь, не прав ли тест: expected.json
сгенерирован скриптом, и если ты менял tools/make-fixtures.mjs, эталон мог
разъехаться с файлами. Перегенерируй: `node tools/make-fixtures.mjs fixtures`.

**API перестал отвечать во время обработки.** Тяжёлый шаг попал в основной
поток. Это самая частая ошибка в этом стеке — смотри §5.2 и перенеси
в worker_threads.

**Появился реальный трек, который не парсится.** Это ценность, а не проблема.
Положи его в fixtures/, добавь тест с ожидаемыми значениями (сверь в GpsDump
или XCTrack) и только потом чини парсер. Набор фикстур только растёт.

**Claude Code хочет сделать больше, чем в задаче.** Откажись и вынеси
в отдельную сессию.

**3D тормозит.** Сначала проверь, не создаются ли Entity на точку и включён ли
requestRenderMode. В 90% случаев дело в одном из двух.
