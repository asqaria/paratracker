# ТЗ: Skyline — платформа 3D-визуализации и анализа парапланерных полётов

**Версия:** 1.0
**Дата:** 2026-09-14
**Статус:** черновик для реализации в Claude Code

> Рабочее название `Skyline` — заменить на финальное перед стартом. В коде используется неймспейс/пакет `skyline`.

---

## 1. Резюме

Веб-платформа (позже + мобильное приложение), куда парапланерист загружает трек-лог со своего прибора и получает:

1. **Кинематографичный 3D-просмотр полёта** на реальном рельефе гор.
2. **Аналитику**: термики, вариометр, ветер, глайды, XC-очки.
3. **Логбук** — личная история полётов со статистикой.
4. **Социальную часть**: публичные ссылки на полёт, лента, сравнение треков.

Ключевое отличие от существующих продуктов — сочетание «красиво» (уровень Ayvri/SkyViz) и «полезно» (уровень SeeYou/XContest) в одном современном интерфейсе, плюс экспорт видео для соцсетей.

### 1.1. Конкурентный контекст (кратко)

| Продукт | Сильное | Слабое |
|---|---|---|
| Ayvri (закрыт) | Эталон 3D-визуала | Больше не существует — ниша свободна |
| XContest | Соревновательная база, скоринг | Устаревший UI, слабое 3D |
| SkyViz | 3D-видео, Strava-оверлеи | Только IGC, мало глубокой аналитики |
| SeeYou / SeeYou Cloud | Глубокая аналитика | Платно, десктопно, для планеристов |
| Flyskyhy / XCTrack | На лету в полёте | Не про пост-анализ и шаринг |

**Вывод:** целимся в «3D-визуал уровня Ayvri + аналитика уровня SeeYou + шаринг уровня Strava».

## 2. Пользователи и сценарии

### 2.1. Персоны

- **P1. Новичок (60% аудитории).** Хочет посмотреть свой полёт красиво и показать друзьям. Не понимает термина «L/D». Метрика успеха: время от загрузки файла до первого «вау» < 30 сек.
- **P2. XC-пилот (30%).** Разбирает полёт: где терял высоту, как обошёл долину, какой был ветер, сколько очков. Сравнивает свой трек с треком более опытного пилота в том же дне.
- **P3. Инструктор / организатор (10%).** Разбор полётов группы, несколько треков на одной карте, комментарии с привязкой к моменту времени.

### 2.2. Ключевые пользовательские истории

```
US-01  Как пилот, я хочу перетащить .igc файл на страницу и сразу увидеть свой полёт в 3D,
       без регистрации.
US-02  Как пилот, я хочу проиграть полёт по времени с камерой, следующей за мной.
US-03  Как пилот, я хочу видеть трек, раскрашенный по скороподъёмности, чтобы понять,
       где были термики.
US-04  Как пилот, я хочу получить список термиков с усилением и набором высоты.
US-05  Как пилот, я хочу расшарить полёт публичной ссылкой с красивым превью в мессенджере.
US-06  Как пилот, я хочу видеть логбук всех своих полётов с суммарной статистикой за сезон.
US-07  Как XC-пилот, я хочу видеть свои XC-очки (FAI-треугольник / свободная дистанция).
US-08  Как инструктор, я хочу наложить 2–5 треков одного дня и проиграть их синхронно.
US-09  Как пилот, я хочу экспортировать 15-секундное вертикальное видео полёта для Instagram.
US-10  Как пилот, я хочу видеть на 3D-сцене границы воздушных пространств и понять,
       не нарушил ли я их.
```

## 3. Входные данные: форматы и устройства

### 3.1. Обязательная поддержка (Фаза 1)

| Формат | Источник | Особенности |
|---|---|---|
| **IGC** | XCTrack, Flymaster, Skytraxx, Syride, Naviter, GpsDump | Основной. Содержит баровысоту — критично для вариометра |
| **GPX** | Garmin, телефоны, Strava | Нет баровысоты (обычно), только GPS-высота |
| **KML/KMZ** | Google Earth, старые приборы | Извлекаем только `<gx:Track>` / `<LineString>` |

### 3.2. Желательная поддержка (Фаза 2+)

| Формат | Источник |
|---|---|
| **FIT** | Garmin (Forerunner, Fenix, Edge) |
| **CSV** | Syride, самописные логгеры — с мастером маппинга колонок |
| **Импорт по ссылке** | XContest URL, Flymaster Live URL |

### 3.3. Спецификация IGC-парсера (критично, реализовать точно)

IGC — построчный текстовый формат. Каждая строка начинается с буквы-типа записи.

**Записи, которые обязательно парсим:**

| Тип | Что | Обязательность |
|---|---|---|
| `A` | Производитель + серийник логгера (первая строка) | Да |
| `H` | Заголовки (метаданные) | Да |
| `I` | Определение расширений B-записи | Да |
| `B` | Точка фиксации (основные данные) | Да |
| `C` | Объявленное задание (waypoints) | Опционально |
| `E` | События (маркеры пилота) | Опционально |
| `L` | Комментарии (некоторые приборы пишут туда полезное) | Опционально |
| `G` | Цифровая подпись | Пропускаем, но сохраняем для валидации |

**Точная структура B-записи (35 байт + расширения):**

```
B 094009 4646616N 01308990E A 01752 01889 ...
│ │      │        │         │ │     │     └─ байты 36+: расширения по I-записи
│ │      │        │         │ │     └─ байты 31-35: GNSS-высота, м (может быть 00000)
│ │      │        │         │ └─ байты 26-30: баровысота (давление), м — ИСПОЛЬЗУЕМ ДЛЯ ВАРИО
│ │      │        │         └─ байт 25: валидность фикса. 'A' = 3D-валид, 'V' = только 2D
│ │      │        └─ байты 16-24: долгота DDDMMmmm + E/W  (9 символов)
│ │      └─ байты 8-15: широта DDMMmmm + N/S  (8 символов)
│ └─ байты 2-7: время UTC HHMMSS
└─ байт 1: тип записи
```

> ⚠️ Позиции 1-based и должны быть реализованы ровно так. Частая ошибка —
> отвести широте 7 символов вместо 8 (забыв букву полушария), после чего вся
> долгота читается со сдвигом. Добавить тест на эталонной строке выше.

**Правила декодирования:**

```
lat  = DD  + (MMmmm / 1000) / 60,  знак: S → отрицательная
lon  = DDD + (MMmmm / 1000) / 60,  знак: W → отрицательная

Дата — из H-записи, поддержать ОБА варианта:
  старый:      HFDTE150726
  с 2016 года: HFDTEDATE:150726,01     ← номер после запятой = полёт за день
Формат DDMMYY. Конвенция (не норма стандарта): YY < 80 → 20YY, иначе 19YY.
Санити-чек обязателен: дата не в будущем и не раньше 1990 — иначе считать
заголовок битым и переходить к fallback (имя файла → вопрос пользователю).

Переход через полночь UTC: если время следующей B-записи < предыдущей, +1 сутки.
Высота может быть отрицательной ("-0012") — обрабатывать.
```

**Заголовки, которые извлекаем:**

| Ключ | Смысл | Куда |
|---|---|---|
| `HFDTE` / `HFDTEDATE:` | Дата полёта (два формата, см. выше) | `flight.date` |
| `HFPLTPILOTINCHARGE` | Имя пилота | `flight.pilot_name_raw` |
| `HFGTYGLIDERTYPE` | Модель крыла | `flight.glider_raw` |
| `HFGIDGLIDERID` | Регистрация | `flight.glider_id` |
| `HFFTYFRTYPE` | Модель прибора | `flight.device` |
| `HFDTM100GPSDATUM` | Датум (ожидаем WGS-1984) | валидация |
| `HFSITSITE` | Место старта | `flight.site_raw` |

**I-запись (расширения B):** формат `I NN SSFFCCC SSFFCCC...`, где `NN` — количество расширений, `SS`/`FF` — начальный/конечный байт (1-based), `CCC` — трёхбуквенный код. Полезные коды:

- `FXA` — точность фикса (м) → фильтрация шума
- `SIU` — число спутников → фильтрация шума
- `GSP` — путевая скорость
- `TAS` — истинная воздушная скорость (редко)
- `VAT` — вариометр от прибора (если есть — использовать как reference, но считать свой)
- `ENL` — Environmental Noise Level, уровень шума. У парамоторов косвенно показывает работу мотора
- `LAD` / `LOD` — дополнительные знаки минут широты/долготы. **Важно:** без них разрешение координат ограничено 0.001 минуты ≈ 1.85 м, что заметно шумит на расчёте радиуса виража. Если расширения присутствуют — обязательно использовать

**Обработка ошибок парсера** — не падать, а деградировать:

```
- Строка не распознана → пропустить, инкрементировать счётчик warnings.
- Нет баровысоты (все 00000) → fallback на GNSS-высоту, поставить флаг
  flight.altitude_source = 'gnss', предупредить пользователя в UI
  ("вариометр менее точен: в файле нет барометрической высоты").
- Нет HFDTE → пытаться извлечь дату из имени файла, иначе спросить пользователя.
- Дубликаты по времени → дедуплицировать, оставить первую.
- Фиксы с 'V' (2D) → помечать, исключать из расчёта вертикальной скорости.
- Файл > 50 МБ или > 500 000 точек → отклонить с понятным сообщением.
```

### 3.4. Нормализованная внутренняя модель трека

Все парсеры приводят к единому виду:

```ts
type TrackPoint = {
  t:       number;   // UNIX timestamp, мс, UTC
  lat:     number;   // градусы, WGS84
  lon:     number;   // градусы, WGS84
  altBaro: number | null;  // м, барометрическая (QNE/ISA)
  altGnss: number | null;  // м, над эллипсоидом WGS84 — парсер пересчитывает из геоида (HFALG, GPX, KML)
  valid:   boolean;  // 3D-фикс
  fxa?:    number;   // точность, м
  siu?:    number;   // спутники
};

type ParsedTrack = {
  points: TrackPoint[];
  meta: { pilot?, glider?, device?, site?, date, timezoneGuess? };
  warnings: string[];
  altitudeSource: 'baro' | 'gnss';
};
```

> ⚠️ **Важно про высоты.** IGC-баровысота — это давление по стандартной атмосфере (1013.25 hPa), а не высота над уровнем моря. Для отрисовки на рельефе использовать GNSS-высоту либо баровысоту, откалиброванную по точке старта (сдвиг = `terrain_elevation(старт) − altBaro(старт)`). Реализовать обе стратегии, по умолчанию — калиброванная баро. Для вариометра — всегда сырая баро (она гладкая, GNSS шумит на ±5–15 м).

## 4. Выбор технологического стека

### 4.1. Выбор стека: как принято решение

Рассматривались три варианта: .NET-бэкенд, TypeScript-монорепо и serverless на Supabase.

**Serverless отпал сразу:** ключевая ценность продукта — качественная аналитика и рендер видео, и то и другое плохо живёт в браузере на телефоне. (Но парсинг и предпросмотр в браузере всё равно нужны — см. §7.1, это даёт «вау за 3 секунды» без регистрации.)

**Выбор между .NET и TypeScript** решили четыре довода — все в пользу TypeScript:

| Довод | Почему это перевешивает |
|---|---|
| **Формат `.track`** | При разделении языков это ДВЕ зеркальные реализации нетривиального бинарного формата (выравнивание колонок, delta-of-delta, таблица разрывов) плюс cross-language round-trip тесты в CI. В монорепо — один пакет, который фронт импортирует напрямую. Это было самое вероятное место будущих багов |
| **XC-скоринг** | `igc-xc-score` — библиотека для Node. На .NET это Docker-сайдкар с HTTP-контрактом, своим деплоем и своим режимом отказа. В TS — `npm install`. Минус целый сервис из архитектуры |
| **Общие типы** | `ParsedTrack`, все DTO API — одно определение, проверяется компилятором с обеих сторон. При разделении они дублируются и расходятся молча |
| **Одна тулчейн-цепочка** | Один `pnpm test`, один линт, одна дорожка CI, один рантайм на VPS |

**Что принесено в жертву:** экспертиза владельца в .NET и производительность числодробилки. Второе не критично — парсинг и анализ вырастут примерно с 8 до 15 core-секунд на полёт (расчёт в §11.4), что при двух ядрах незаметно даже на тысяче полётов в день.

> **Условие, при котором решение надо пересмотреть:** если проект станет продуктом JATE и над ним будут работать нанятые .NET-разработчики, экспертиза в компании перевесит всё перечисленное. Для проекта, который ведёт один человек, — нет.

### 4.2. Итоговый стек

```
Монорепо:   pnpm workspaces + Turborepo
Язык:       TypeScript, strict, везде
API:        Fastify 5 + Zod (схемы = валидация + выводимые типы)
ORM:        Drizzle ORM; PostGIS-геометрия через raw SQL и кастомные типы
БД:         PostgreSQL 17 + PostGIS 3.5
Очередь:    внутрипроцессная + восстановительный проход при старте (см. ниже)
Хранилище:  S3-совместимое (MinIO локально / Cloudflare R2 в проде)
Фронт:      React 19 + Vite + Tailwind v4 + Zustand + TanStack Query
3D:         CesiumJS
Тесты:      Vitest везде; Playwright для e2e
```

**Почему Fastify, а не NestJS.** NestJS ближе к привычной владельцу структуре (модули, DI, декораторы ≈ Clean Architecture с MediatR), но добавляет слой магии и косвенности, который на проекте такого размера окупается плохо, а отладку усложняет. Слоистость даётся обычными папками пакетов (`core` / `parsing` / `analysis` / `db`) без фреймворка. Если по ходу окажется, что структуры не хватает — NestJS остаётся запасным вариантом, миграция несложная.

**Почему Drizzle, а не Prisma.** У Prisma слабая поддержка PostGIS — геометрию всё равно пришлось бы писать raw-запросами, теряя типизацию. Drizzle ближе к SQL и позволяет описать `geography` кастомным типом.

**Очередь обработки.** BullMQ на первом этапе избыточен. Вместо него: статус в таблице `flights` — единственный источник правды, а при старте воркера выполняется восстановительный проход, который заново ставит в очередь всё, застрявшее в `pending` и `parsing`. Это даёт устойчивость к перезапуску без внешней зависимости. BullMQ добавляется, когда воркеров станет больше одного.

> ⚠️ **Главный риск перехода на Node — блокировка event loop.** FAI-скоринг может считаться до 120 секунд (§6.6), парсинг и анализ — десятки секунд. Синхронный код такой длины остановит весь процесс. **Все CPU-тяжёлые шаги конвейера обязаны исполняться в пуле `worker_threads`**, а не в основном потоке воркера. Это не оптимизация, а условие работоспособности.

**Структура монорепо:**

```
/apps
  api/            Fastify: HTTP, auth, DTO
  worker/         конвейер обработки треков + пул worker_threads
  web/            React + Vite + CesiumJS
  render/         Puppeteer + ffmpeg → MP4 (Фаза 4)
/packages
  core/           домен: типы, ParsedTrack, DTO-схемы Zod, константы
  parsing/        IgcParser, GpxParser, KmlParser, FitParser
  analysis/       CircleDetector, ThermalDetector, GlideDetector, WindEstimator
  track-format/   чтение и запись .track — используют и worker, и web
  db/             Drizzle-схема, миграции, репозитории
/fixtures         эталонные IGC/GPX + expected.json
/tools            генератор фикстур и прочие скрипты
/infra            docker-compose, деплой
/docs/SPEC.md
```

Слои те же, что в Clean Architecture, только границы проходят по пакетам, а не по проектам: `core` — домен, `parsing`/`analysis`/`track-format` — приложение, `db` — инфраструктура. Правило зависимостей прежнее: `core` не зависит ни от чего.

**Мобильное (Фаза 5)** — сначала PWA (share target для `.igc`, offline-логбук), затем React Native при подтверждённом спросе.

### 4.3. Выбор 3D-движка

| Движок | Вердикт |
|---|---|
| **CesiumJS** | ✅ **Выбран для 3D-просмотрщика.** Настоящий эллипсоидальный глобус, quantized-mesh terrain, корректная работа с высотами в метрах, `Entity`/`Primitive` API, готовая система камер, `Clock`+`SampledPositionProperty` для проигрывания по времени из коробки, `PolylineVolume`/`WallGraphics` для «занавеса» под треком. |
| **MapLibre GL JS** | ✅ **Выбран для 2D-видов**: логбук на карте, тепловая карта термиков, выбор области. Terrain-DEM есть, но объекты в воздухе на заданной абсолютной высоте — костыльно. |
| **deck.gl** | Рассмотреть для слоя «тысячи треков сообщества» (`TripsLayer`, `PathLayer`) поверх MapLibre. Не для основного просмотрщика. |
| **Three.js / R3F** | Только если понадобится полностью кастомный визуал (стилизованный «низкополигональный» мир). Тогда весь рельеф, тайлы и геопривязку пишем сами — дорого. Не на старте. |
| **Unreal Engine / Unity** | ❌ **Отклонены для основного продукта.** Развёрнутое обоснование ниже — вопрос возникает регулярно. |

#### Почему не Unreal Engine (и не Unity)

**Веб-дистрибуция — это и есть продукт.** Ключевой сценарий: пилот кидает ссылку в чат клуба, её открывают с телефонов и ноутбуков без установки чего-либо. Всё остальное подчинено этому.

**1. У Unreal нет веб-экспорта.** Epic удалил поддержку HTML5 в UE 4.24 (2019) и передал её сообществу. В UE5 официального экспорта в браузер нет. Существуют форки под WebAssembly/WebGPU и обсуждения на форумах Epic, но это не продакшн-уровень.

**2. Остаётся Pixel Streaming — и его экономика несовместима с моделью продукта.** UE исполняется на GPU-сервере и стримит видео через WebRTC. У managed-провайдеров это порядка €99/мес за 2 одновременных пользователя плюс ~€45/мес за каждого следующего; на своём парке GPU дешевле, но порядок тот же — один GPU на 1–3 сессии.

Приложим к нашему сценарию: один популярный полёт, расшаренный в чат, — это несколько десятков открытий за вечер. На CesiumJS это несколько десятков запросов к CDN. На Pixel Streaming — несколько десятков одновременных GPU-сессий, то есть сотни евро за один удачный трек. Виральность, ради которой строится Фаза 3–4, превращается из актива в статью расходов, растущую линейно.

Плюс сопутствующее: задержка, расход трафика на мобильных, холодный старт инстанса на каждое открытие ссылки (а обещанный в §7.1 «вау за 3 секунды» при этом недостижим).

**3. Unity.** WebGL-экспорт существует, но: 20–40 МБ загрузки до первого кадра, и вся геопространственная часть (стриминг тайлов, эллипсоидальная система координат, terrain LOD) слабее — её пришлось бы строить самостоятельно поверх того же Cesium. Выигрыша против CesiumJS нет.

**4. Главное — «красиво» упирается не в движок.** Рычаги визуального качества здесь: разрешение спутниковой подложки, качество DEM, настройка атмосферы/освещения/тумана и работа камеры (§7.6). Бюджет, вложенный в хорошую imagery по целевому региону, даёт больше, чем смена рендерера. Cesium поддерживает атмосферу, положение солнца по времени суток, тени и туман — вопрос art direction.

**Где Unreal действительно уместен — Фаза 4, серверный рендер видео.** Там интерактивность не нужна (пользователь и так ждёт в очереди), а качество картинки — весь смысл фичи. Связка **Cesium for Unreal + Movie Render Queue** даёт объёмные облака, честную атмосферу, motion blur и глубину резкости — то, что headless Chromium + CesiumJS не воспроизведёт.

Условие для этого апгрейда: фича экспорта видео из Фазы 4 подтвердила спрос и стала платным драйвером. Тогда `apps/render` переписывается на UE как **изолированный фоновый сервис**, при неизменном фронтенде. Архитектурное следствие для Фазы 4: контракт сервиса рендера (`POST /render` → jobId → MP4) должен быть движко-независимым, чтобы такая замена не затронула ничего, кроме самого сервиса.

>
> 1. **Вертикальный датум — EGM2008 (ортометрические высоты над геоидом).**
>    CesiumTerrainProvider и quantized-mesh ожидают высоты **над эллипсоидом WGS84**.
>    Без пересчёта геоид → эллипсоид рельеф уедет на величину ундуляции геоида:
>    в районе Заилийского Алатау это около −45…−50 м. Результат — трек
>    систематически «под землёй» или висит над ней, и весь `altAgl` врёт.
>    Пересчёт: `h_эллипс = H_орто + N(lat, lon)`, где `N` — модель геоида EGM2008.
> 2. **GLO-30 — это DSM, а не DTM:** включает лес и застройку. В лесистых зонах
>    AGL будет занижен на высоту полога (10–25 м). Для показа «высоты над землёй»
>    это приемлемо, но в UI не обещать точность лучше ±25 м.

> **Архитектурное требование:** источник рельефа за интерфейсом `ITerrainProvider` с конфигом через env. Смена провайдера не должна требовать правок в коде сцены.

### 5.2. Конвейер обработки полёта

```
1. UPLOAD     Клиент кладёт файл → POST /api/v1/flights/upload (multipart)
              → сырой файл в S3: raw/{userId}/{flightId}.igc
              → строка в БД: flights (status = 'pending')
              → возвращается flightId, клиент подписывается на SSE

2. PARSE      Worker: определить формат → распарсить → ParsedTrack
              → валидация, фильтрация выбросов
              status = 'parsing'

3. CLEAN      - Медианный фильтр по координатам (окно 3) — убрать одиночные выбросы
              - Отбросить фиксы с fxa > 50 м или siu < 4 (если поля есть)
              - Ресэмплинг на равномерную сетку 1 Гц (линейная интерполяция),
                пропуски > 30 с помечаются как разрывы (gap)
                ⚠️ Интерполяция корректна только при исходной частоте ≥ 0.2 Гц
                   (шаг ≤ 5 с). GPX с телефонов и Garmin часто имеет шаг 5–10 с:
                   там интерполяция срежет виражи хордами, накопление курса не
                   наберёт 360°, и детекция термиков просто не сработает.
                   Правило: медианный шаг > 4 с → выставить флаг
                   flight.analysis_level = 'basic', термики и ветер НЕ считать,
                   в UI честно написать «трек слишком редкий для детекции
                   термиков — показаны только высота, скорость и маршрут».
              - Сглаживание высоты фильтром Савицкого–Голея (окно 9, полином 2)

4. DERIVE     Производные величины на каждую точку — чистые функции
              из packages/analysis, без сети и БД:
              vSpeed (м/с), groundSpeed (м/с), heading (°), turnRate (°/с)

4b. AGL       altAgl — высота над рельефом. ОТДЕЛЬНЫЙ шаг в воркере, а не
              в packages/analysis: требует запроса к DEM, то есть сети.
              Массив высот рельефа передаётся в analysis уже готовым.

5. SEGMENT    status = 'analyzing'
              Детекция фаз: старт, термик, глайд, восьмёрки, посадка (§6)

6. SCORE      igc-xc-score в worker_thread → XC-очки, тип маршрута, ППМ
              Синхронно только для FFVL/XContest (бюджет 5 с).
              FAI Sporting Code — отдельной фоновой задачей, см. §6.6

7. AGGREGATE  Сводка полёта: длительность, дистанция, max/min высота,
              max набор, лучший термик, средний L/D, XC-очки

8. AIRSPACE   Проверка пересечений с воздушным пространством (PostGIS ST_3DIntersects)

9. PACK       Сформировать бинарный .track для фронта (§5.4) → S3
              Сгенерировать превью WebP (для OG-тегов) → S3

10. DONE      status = 'ready', SSE-событие клиенту
```

> ⚠️ **Шаги 2–6 и 9 исполняются в пуле `worker_threads`, не в основном потоке.**
> Каждый из них занимает процессор на секунды-десятки секунд; в основном потоке
> это остановит и приём новых задач, и SSE-поток статусов. Основной поток воркера
> только раздаёт задания и пишет статусы в БД.
>
> **Восстановление после перезапуска:** при старте воркер выбирает из `flights`
> всё со статусом `pending`, `parsing` или `analyzing` и ставит заново. Без этого загруженный
> перед падением файл навсегда зависнет в `pending`.

**Целевое время конвейера:** 4-часовой полёт (14 400 точек) — не более **15 секунд** на шаги 2–9, из них скоринг FFVL/XContest ≤ 5 с (он самый тяжёлый).

**Замер (Фаза 1, задача 1.5).** Реализованы шаги 2–4 и 9 (parse → clean → derive → pack); шагов 5–8 (сегментация, скоринг, агрегаты, воздушное пространство) ещё нет. Живые Postgres и MinIO, пул `worker_threads`, загрузка через `POST /api/v1/flights/upload`:

| Трек | Загрузка (ответ 202) | Загрузка → `ready` | Счёт в потоке |
|---|---|---|---|
| `baseline.igc`, 960 точек | 64 мс | 198 мс | 3 мс |
| 4 часа, 14 400 точек | 25 мс | 76 мс | 25 мс |

Короткий трек «медленнее» сквозняком, потому что в его 198 мс попадает первый запуск потока (~150 мс: импорт `parsing`, `analysis`, `track-format`); дальше пул разогрет. Поэтому таймаут шага (30 с, §11.2) отсчитывается с момента готовности потока, а не с его создания. Вывод: бюджет 15 секунд определяется скорингом, а не разбором и аналитикой — их вклад на порядки меньше.

### 5.3. Стратегия хранения трек-поинтов (важное решение)

**Не хранить точки построчно в реляционной таблице.** 10 000 полётов × 15 000 точек = 150 млн строк — медленно и дорого без нужды.

**Вместо этого:**

| Что | Где | Формат |
|---|---|---|
| Сырой файл | S3 | как загружен, для перепарсинга при изменении алгоритмов |
| Готовый трек для фронта | S3 + CDN | бинарный `.track` (§5.4), gzip/brotli |
| Упрощённая геометрия | PostgreSQL | `geography(LineStringZM, 4326)`, упрощена Дугласом–Пекером до ~500 точек — для карт, поиска по области, кластеризации |
| Агрегаты | PostgreSQL | колонки в `flights` |
| Сегменты (термики/глайды) | PostgreSQL | таблицы `thermals`, `glides` — их сотни, не тысячи; нужны для аналитики по сезону и тепловых карт |

### 5.4. Бинарный формат `.track` (фронт)

Цель: 15 000 точек должны грузиться и разворачиваться в типизированные массивы без `JSON.parse`.

```
Заголовок (64 байта):
  magic       4B  "SKTR"
  version     2B  uint16 = 1
  pointCount  4B  uint32
  t0          8B  float64 — UNIX ms первой точки
  lat0,lon0   16B float64 ×2 — опорная точка (origin) для смещений
  fields      2B  битовая маска присутствующих каналов
  gapCount    2B  uint16 — число разрывов (см. ниже)
  reserved    ...

Тело — колоночное (SoA), не построчное. КАЖДАЯ КОЛОНКА ВЫРОВНЕНА ПО 8 БАЙТ
(добить нулями в хвосте), иначе new Int32Array(buffer, offset, n) бросит
RangeError при нечётном pointCount:

  dt          Uint16Array[n]   — Δt от предыдущей точки, мс. Потолок 65 535 мс!
                                 Разрыв больше этого кодируется как 0xFFFF,
                                 фактическая длительность — в таблице разрывов.
  dLat        Int32Array[n]    — (lat − lat0) × 1e7, дельта-от-дельты (см. ниже)
  dLon        Int32Array[n]    — (lon − lon0) × 1e7, дельта-от-дельты
  alt         Int16Array[n]    — метры
  vSpeed      Int16Array[n]    — м/с × 100
  gSpeed      Uint16Array[n]   — м/с × 100  (потолок 655 м/с, с запасом)
  heading     Uint16Array[n]   — градусы × 100
  altAgl      Int16Array[n]    — метры
  flags       Uint8Array[n]    — бит 0: gap, бит 1: в термике, бит 2: 2D-фикс

Хвост: таблица разрывов, gapCount × { index: Uint32, durationMs: Uint32 }
```

**Кодирование координат.** Хранить не абсолютное смещение от origin, а
**delta-of-delta**: первое значение — смещение от `lat0`, дальше — разность
с предыдущей разностью. Пилот летит плавно, вторая разность мала и почти
постоянна, поэтому колонка становится сжимаемой. При абсолютных смещениях
brotli даст лишь ~50–60% от исходного, при delta-of-delta — ~25–30%.

**Размер.** 2+4+4+2+2+2+2+2+1 = **21 байт/точку**.
15 000 точек ≈ **315 КБ** сырых, ≈ **90–100 КБ** после brotli.

Для сравнения — тот же трек в JSON:

| Представление | Размер |
|---|---|
| `.track` (brotli) | ~95 КБ |
| GeoJSON `LineString`, только `[lon,lat,alt]` | ~0.5 МБ |
| GeoJSON `FeatureCollection`, точка-`Feature` со всеми каналами в `properties` | ~3.5 МБ |

То есть выигрыш против «наивного» GeoJSON — более чем в 30 раз, против
минимального `LineString` — примерно в 5 раз, **плюс** главное: результат
разворачивается прямо в типизированные массивы без `JSON.parse` и без
последующего прохода по массиву объектов.

> Реализация одна — `packages/track-format`, экспортирует `writeTrack()` и `readTrack()`. Воркер пишет, фронт читает, тип буфера общий. Round-trip тест обычный unit-тест внутри пакета; отдельного слоя синхронизации между языками нет — это и было главным доводом за монорепо (§4.1).

## 6. Аналитика полёта — спецификация алгоритмов

Все алгоритмы — в `packages/analysis`, каждый отдельным модулем, каждый покрыт unit-тестами на эталонных IGC-файлах. Функции чистые: вход — массив точек, выход — результат, без обращений к БД и сети. Это позволяет гонять их в `worker_threads` и тестировать без окружения.

### 6.1. Вертикальная скорость (вариометр)

```
Вход:  сглаженная баровысота h[i] на равномерной сетке 1 Гц
Метод: центральная разность по окну ±N/2 секунд
       vz[i] = (h[i + N/2] − h[i − N/2]) / N

Три канала, все три сохраняем:
   N = 2 с   — «мгновенное» варио, для графика и раскраски трека
   N = 4 с   — демпфированное, для расчёта термиков (меньше шума)
   N = 20 с  — «интегральное», сопоставимо с показаниями приборов
               (XCTrack, Flytec, Flymaster усредняют 10–30 с).
               Нужно, иначе пилот сравнит цифру в приложении с тем, что видел
               в полёте на приборе, и решит, что приложение врёт.
```

### 6.2. Детекция кругов (виражей)

```
1. heading[i] = азимут от точки i к i+1
2. Δheading[i] = нормализованная в (−180, 180] разница heading[i] − heading[i−1]
3. Скользящее накопление: если |Σ Δheading| по окну достигает 360°
   с сохранением знака — зафиксирован полный круг.
4. Круг характеризуется: центр, радиус, период (сек), направление (CW/CCW),
   набор высоты. Центр и радиус — подгонкой x(τ) = a + b·τ + A·sin ωτ + B·cos ωτ
   по каждой оси (ω — фактическая угловая скорость: накопленный поворот /
   длительность). «Среднее координат и медиана расстояний» врёт на ±5 м при
   сносе 1.5 м/с — центр уезжает за оборот; остаётся запасным вариантом.

Отсечки от ложных срабатываний (по типу ЛА, CIRCLE в core/constants.ts):
   - радиус 15–120 м, период 10–35 с — параплан; дельтаплан и планер —
     предварительные пределы по формуле координированного виража
   - направление не меняется внутри круга; откат курса меньше 10° за шаг —
     шум округления IGC (0.001′ ≈ 1.85 м на хорде 10 м), а не смена направления
   - окно дольше предела периода сжимается с начала без подгонки
   - сильный ветер: против ветра пилот раз за круг почти стоит над землёй, курс
     по земле там не наблюдаем. Шаги короче 3 м пропускаются (до 3 с подряд),
     поворот через них — в сторону текущего виража; допуск отката курса растёт
     на коротких шагах как atan(1.85 м / длина шага)
```

### 6.3. Детекция термиков

```
Термик = последовательность ≥ 1.5 кругов подряд со средним vz > 0.2 м/с,
         с допуском разрыва ≤ 15 секунд между кругами, длительностью ≥ 60 с.
         (60 с — по разметке владельцем реальных полётов: пара кругов на 30–50 с
         с набором 20–50 м — «слабый пузырь», не термик.)

Метрики каждого термика:
   startTime, endTime, duration
   entryAlt, exitAlt, gain = exitAlt − entryAlt
   avgClimb = gain / duration          [м/с]  ← основной показатель
   maxClimb = max(vz) внутри           [м/с]
   turnCount, avgRadius, direction
   driftVector = (exitCenter − entryCenter) / duration  → оценка ветра
       ⚠️ Это направление, КУДА сносит (куда дует ветер).
          В §6.5 и в колонке wind_dir_deg хранится метеорологическое
          направление — ОТКУДА дует, то есть driftDir + 180°.
          Конвертировать явно, иначе два метода оценки ветра разойдутся на 180°.
   efficiency = avgClimb / maxClimb    ← «насколько чисто центрировал» (0..1)

Классификация: слабый (<1 м/с), средний (1–3), сильный (3–5), мощный (>5)

«≥ 1.5 круга» при полных кругах §6.2: к группе кругов добавляется доворот до
первого и после последнего — пока пилот поворачивает в ту же сторону не
медленнее половины угловой скорости самого медленного круга (в среднем за 3 с:
одиночный нулевой шаг курса после округления IGC — не выход на прямую).
turnCount = полные круги + доворот / 360°; этими же точками ограничен термик.
driftVector делится не на duration, а на время между серединами первого и
последнего кругов — центры относятся к серединам оборотов. Один круг — снос null.

Разрыв между кругами дольше 15 с — тот же термик, если пилот за разрыв набирал
(средний набор больше 0.2 м/с) и разрыв не дольше 90 с: в ветре пилот выпадает
из ядра и ищет его широкими кругами, не выходя из подъёма. Основание — разметка
владельцем реального полёта: 11 минут непрерывного набора с паузами до 67 с —
один термик.

Границы термика — не крайние круги, а начало и конец набора: до первого круга
и после последнего граница сдвигается, пока средний набор за 20 с (окно
«интегрального» варио, §6.1) больше 0.2 м/с. Разметка владельца: после кругов
пилот 5 минут набирал по прямой (+760 м) — это тот же термик. Два термика,
между которыми набор не прерывался, — один; сомкнулись только доворотами на
снижении — два. Набор по прямой вовсе без кругов термиком не считается
(динамик, волна).
```

### 6.4. Детекция глайдов (переходов)

```
Глайд = переход: от взлёта или конца термика до начала следующего термика
        или посадки, длительностью ≥ 30 с (короче — из термика сразу в соседний).
   Первый глайд — от старта, последний — финальный глайд до посадки. Взлёт и
   посадка — по путевой скорости (выше 4 м/с, державшейся 30 с, FLIGHT в
   core/constants.ts): подъём пешком и уход с посадки в глайд не входят.
   Круги поиска и пузыри, не ставшие термиком (§6.3), — часть перехода: так
   делят полёт на «кружение» и «переход» SeeYou и XCTrack. Нарезка кругами
   дробила бы один перелёт от облака к облаку на куски с завышенным качеством.

Метрики:
   distance (путь по земле, м — сумма шагов трека, через разрывы записи не
            набегает), duration, altLoss
   glideRatio = distance / altLoss     ← аэродинамическое качество по факту
   avgGroundSpeed = distance / duration, avgVz = −altLoss / duration
   heading — азимут от начала к концу
   headingConsistency — насколько прямо шёл: расстояние по прямой / путь (0..1)
   netEfficiency — сравнение с поляризацией крыла (Фаза 3, нужен профиль крыла)

⚠️ glideRatio не определён при altLoss ≤ 0. Такое бывает регулярно: динамик
   вдоль гряды, слабый подъём без виражей — пилот идёт прямо и НАБИРАЕТ.
   Правила:
     altLoss < 50 м  → glideRatio = null, в UI «—», глайд помечается как
                       'dynamic' и исключается из расчёта среднего качества
     иначе           → значение клипуется сверху на 60
   В схеме БД колонки glide_ratio / avg_glide_ratio — numeric(6,2) и nullable
   (numeric(4,2) переполнится: максимум 99.99).
```

### 6.5. Оценка ветра

Два независимых метода, результаты сверяются:

```
Метод A (дрейф термика): вектор смещения центра круга за время термика.
   Прост, но даёт средний ветер по слою набора.

Метод B (подгонка окружности в пространстве скоростей):
   В штиль путевая скорость в вираже постоянна. При ветре GS(heading) описывает
   окружность, смещённую от начала координат на вектор ветра.
   → Метод наименьших квадратов: подобрать (Wx, Wy, Vair), минимизируя
     Σ (|GS_i − W| − Vair)²
   Задача НЕЛИНЕЙНАЯ. Решать Левенбергом–Марквардтом или фитом Таубина.
   Алгебраический фит Kåsa НЕ подходит — он минимизирует другую функцию
   и систематически занижает радиус на неполных дугах.
   Даёт ветер на каждой высоте набора → профиль ветра по высоте.

Реализация (packages/analysis/wind.ts, пороги — WIND в core/constants.ts):
   - Метод B — на каждом круге §6.2. Путевая скорость — центральной разностью
     координат, а не по курсу: против ветра пилот почти стоит, курс не наблюдаем.
     Kåsa — только начальное приближение для Левенберга–Марквардта.
   - Центральная разность — хорда дуги: вращающаяся часть скорости короче в
     sin(ωΔ)/(ωΔ) раз (−1.6 % при круге за 20 с). Центр (ветер) не сдвигается,
     радиус (воздушная скорость) делится на этот множитель.
   - Отбраковка круга: меньше 8 отсчётов; воздушная вне пределов типа ЛА
     (параплан 5–25 м/с); ветер не меньше воздушной; невязка больше 25 % Vair.
   - Профиль: слои по 250 м (границы кратны 250, высоты над эллипсоидом), ветер
     слоя — среднее векторов кругов; confidence = min(1, кругов / 3) ×
     max(0, 1 − разброс / 3 м/с).
   - Метод A сверяется с B по каждому термику: среднее B по его кругам против
     сноса; расхождение |A − B| сохраняется. Ветер полёта (flights.wind_*) —
     среднее B по всем принятым кругам.

Выход: массив { altitudeBand: [м], windSpeed: м/с, windDir: °, confidence: 0..1 }
   windDir — МЕТЕОРОЛОГИЧЕСКОЕ направление, откуда дует. Единая конвенция
   во всей системе: БД, API, UI. Метод A конвертирует свой driftDir → +180°.
Визуализация: «роза ветров по высотам» + стрелки на 3D-сцене.
```

Правила: FFVL, XContest, FAI-Sporting-Code, XCLeague — выбираются пользователем.

## 7. Фронтенд: 3D-просмотрщик

### 7.1. Мгновенный предпросмотр без регистрации (ключевая фича)

```
Пользователь бросает .igc на лендинг
  → Web Worker парсит его прямо в браузере (порт парсера на TS, ~200 строк)
  → через ~1 с рисуется трек в 3D с базовым рельефом
  → фоном файл уходит на сервер
  → когда придёт полная аналитика — сцена достраивается термиками, ветром, очками
  → баннер «Сохраните полёт в логбук → войти»
```

Это даёт «вау» до любых форм регистрации и резко поднимает конверсию.

### 7.2. Слои 3D-сцены

| Слой | Описание | Фаза |
|---|---|---|
| **Terrain** | Quantized-mesh рельеф, вертикальное преувеличение 1.0 (настраивается 1.0–2.0, см. предупреждение ниже) | 1 |
| **Imagery** | Спутниковая подложка; переключатель «спутник / топо / стилизованный» | 1 |
| **Track line** | Основной трек, толщина 3–5 px (на телефоне — 2 px: ширина < 640 или высота < 500) + отдельный слой свечения (см. §7.3). Переключатель «Весь / Пройденный»: во втором режиме линия и тень — только от старта до пилота; линия и край «занавеса» кончаются у пилота в каждом кадре, между точками записи — без ступенек | 1 |
| **Track color** | Раскраска по каналу: вариометр / высота / скорость / время | 1 |
| **Ground shadow** | Проекция трека на рельеф, полупрозрачная тёмная линия | 1 |
| **Curtain wall** | Вертикальный «занавес» от трека до земли — даёт мощное ощущение высоты. Только в камерах Side и Free: из Chase/Cockpit стены видны с торца, из Top — вырождаются в линию. Нейтральный цвет (палитра варио — единственный «кричащий» элемент, §8.1); почти ровная прозрачность (0.2 у трека, 0.12 у земли) и плотная кромка у рельефа — видно, где стена встала на землю, и высота читается как расстояние от линии до кромки. Только на переходах: в термике спираль складывается в белые «башни», термик отмечен колонной. «Пройденный» — край идёт за пилотом. Переключатель «Занавес»; на телефоне по умолчанию выключен (§5.3) | 2 |
| **Glider model** | glTF-модель параплана (своя, генерируется `tools/make-paraglider.mjs`, ~230 КБ, ~9 тыс. треугольников: надутые ячейки, входные отверстия, рисунок-шеврон носом по курсу, стропы каскадом, пилот в куртке, штанах, ботинках, перчатках и шлеме с визором — в коконе в полёте и стоя на земле; области раскраски купола — отдельные материалы `canopy-*` под выбор расцветки крыла, 2.13), ориентированная по курсу сглаженной траектории + крен координированного виража tan(крен) = v·ω/g, не больше 60°; на земле — без крена. Позы по состоянию (glider-pose.ts): до старта идёт с рюкзаком или стоит у разложенного крыла, разбег 6 с — крыло поднимается над головой маятником вокруг подвески, в полёте — кокон, после касания купол опадает за 3 с, потом стоит у крыла или уходит с рюкзаком. Узлы модели (купол, кокон, пилот стоя, ноги, рюкзак) переключаются nodeTransformations, шаг — качание ног. Не мельче 24 px на экране, но не крупнее реального больше чем в 3 раза: иначе издалека модель раздувалась, и круги термиков казались мелкими | 2 |
| **Thermal markers** | Полупрозрачные колонны в местах термиков: от высоты входа до выхода (высота = набор), ось — от центра кругов в начале к центру в конце (наклон = снос ветром), радиус — средний круг, цвет — средний набор по палитре варио. Один Primitive, цилиндр на экземпляр. Колонна, в которой пилот, со стороны (Free, Top) подсвечена, в следящих камерах скрыта — камера у её стенки. Переключатель «Термики на сцене» — в панели аналитики | 2 |
| **Wind arrows** | Стрелки по высотам в углу сцены или в точке пилота | 3 |
| **Airspace** | Полупрозрачные экструдированные полигоны, красная подсветка при нарушении | 3 |
| **XC route** | Полигон маршрута + маркеры ППМ | 3 |
| **Multi-track** | До 8 треков, разные цвета, синхронное проигрывание | 3 |
| **POI** | Точка старта, посадки, рекорд высоты — подписанные билборды | 2 |

> ⚠️ **Вертикальное преувеличение.** `Scene.verticalExaggeration` в Cesium
> применяется к глобусу и 3D Tiles, но **не** к позициям `Entity` и `Primitive`.
> При exaggeration 1.5 рельеф поднимется, а трек, его тень и «занавес» останутся
> на истинных высотах — сцена развалится. Поэтому при включённом преувеличении
> приложение обязано пересчитать высоты трека само по той же формуле
> `h' = (h − relativeHeight) × k + relativeHeight` и перестроить
> `SampledPositionProperty`. Покрыть тестом: при k = 1.0 и k = 2.0 расстояние
> от точки трека до рельефа под ней должно масштабироваться одинаково.

### 7.3. Раскраска трека по вариометру

```
Дивергентная шкала, центр = 0 м/с.
Диапазон: −5 … +5 м/с (клипуется), с возможностью авто-масштаба по перцентилям 5/95.

  −5 м/с ── насыщенный синий/фиолетовый
  −1 м/с ── приглушённый синий
   0 м/с ── нейтральный серый (НЕ белый — плохо читается на облаках/снегу)
  +1 м/с ── тёплый жёлтый
  +5 м/с ── насыщенный красный/пурпурный

Реализация — строго так (не сегментами-энтити, 15 000 энтити убьют FPS):

  new GeometryInstance({
    geometry: new PolylineGeometry({
      positions, width, colors, colorsPerVertex: true,  ← вершинные цвета ЗДЕСЬ
      arcType: Cesium.ArcType.NONE,                     ← прямые отрезки в 3D
      vertexFormat: PolylineColorAppearance.VERTEX_FORMAT  ← без этого цветов не будет
    })
  })
  → new Primitive({ geometryInstances, appearance: new PolylineColorAppearance() })

⚠️ НЕ ColorGeometryInstanceAttribute — он задаёт ОДИН цвет на GeometryInstance,
   а не цвет на вершину. Это разные механизмы, их часто путают.

⚠️ Свечение (glow) несовместимо с вершинными цветами в одном примитиве:
   PolylineGlowMaterialProperty требует PolylineMaterialAppearance, который
   вершинные цвета не читает. Решение — ДВА наложенных примитива:
     слой 1 (под): широкая линия, один приглушённый цвет, glow-материал
     слой 2 (над): тонкая линия с вершинными цветами по варио
   Либо кастомный Appearance с собственным шейдером (дороже, отложить).

Обязательно: легенда с числовой шкалой. Палитра должна оставаться различимой
при дейтеранопии — проверить симулятором.
```

### 7.4. Режимы камеры

| Режим | Поведение |
|---|---|
| **Free** | Свободная камера: левая кнопка / один палец — облёт вокруг пилота, правая — сдвиг карты, колесо / щипок — зум, средняя / два пальца — наклон |
| **Chase** | Камера позади пилота на расстоянии D (5–200 м, колесо), по курсу перемещения: направление между центрами тяжести позиций за два соседних окна по 20 с — в термике держит снос, а не обходит круг. Поворот к курсу — критически демпфированной пружиной, τ ≈ 2 с экранного времени (не полётного — иначе на ×16…×60 сглаживания нет; не экспонентой — она срывает камеру с места рывком). Камера смотрит не на сырую точку пилота (у интерполяции скорость скачет на каждом фиксе), а на сглаженную траекторию: локальная линейная регрессия по фиксам с ядром (1 − u²)³, окно ±0,5 с экрана (не меньше ±4 с полёта) |
| **Side** | Вид сбоку: камера слева от курса перемещения (курс − 90°), почти горизонтально, 320 м (50–2000 м). Профиль полёта — наборы и глайды; пилот летит по экрану слева направо |
| **Cockpit** | Вид от первого лица, горизонт стабилизирован |
| **Orbit** | Камера вращается вокруг текущей позиции с настраиваемой скоростью |
| **Top** | Вид сверху, следит за пилотом, без вращения |
| **Cinematic** | Автомонтаж (см. §7.6) |

**Технически:** `Viewer.trackedEntity` + `Entity.position = SampledPositionProperty` с `LagrangePolynomialApproximation` (степень 2) — даёт гладкое движение между фиксами. `Viewer.clock` управляет временем; он же — единый источник правды для синхронизации с графиками.

### 7.5. Таймлайн и графики

```
┌─────────────────────────────────────────────────────────────┐
│  ▶  ⏸   ×1 ×2 ×4 ×8 ×16 ×60        14:32:07   2 840 м      │
│  ├──────────●──────────────────────────────────────────┤    │  ← скраббер
│  График высоты (area chart, залит градиентом по варио)      │
│  ▂▃▅▇█▇▅▃▂▃▅▇█▇▆▅▄▃▂▁                                       │
└─────────────────────────────────────────────────────────────┘
```

- Двусторонняя синхронизация: скраббер ↔ 3D-сцена ↔ курсор на графике.
- Переключаемые каналы графика: высота, вариометр, скорость, AGL, курс.
- Термики подсвечены полосами на оси времени.
- Клик по термику в списке → камера перелетает туда, время устанавливается на вход.
- Горячие клавиши: `Space` — play/pause, `←/→` — ±1 с, `Shift+←/→` — ±1 мин, цифры — режимы камеры (`1–5`: Chase, Side, Free, Cockpit, Top; `1–7`, когда появятся Orbit и Cinematic).

### 7.6. Кинематографичный автомонтаж (Фаза 4)

```
Алгоритм построения «фильма» из трека:
  1. Разбить полёт на сцены по событиям: взлёт, первый термик, лучший термик,
     самая длинная глайда, рекорд высоты, финальный заход, посадка.
  2. Каждой сцене назначить тип камеры и длительность:
     взлёт → низкий орбит 3 с; термик → орбитальный подъём 4 с;
     глайд → chase с ускорением времени 5 с; рекорд высоты → широкий пролёт 3 с;
     посадка → chase→top 3 с.
  3. Между сценами — сглаженные переходы камеры по кривой Безье
     (Cesium camera.flyTo с кастомным easing).
  4. Наложить титры: название места, дата, ключевые цифры.

Экспорт видео:
  - Клиентский: MediaRecorder API + захват canvas → WebM. Быстро, но качество
    зависит от машины пользователя.
  - Серверный (apps/render): headless Chromium + CesiumJS рендерит покадрово
    в офскрин, ffmpeg собирает H.264 MP4. Форматы 16:9, 9:16, 1:1.
    Медленно (1–3 мин на 30 с видео) → очередь + уведомление по готовности.
    → Платная фича.
```

### 7.7. Производительность — жёсткие требования

| Метрика | Цель |
|---|---|
| FPS на сцене с 1 треком, ноутбук со встроенной графикой | ≥ 50 |
| FPS с 8 треками | ≥ 30 |
| Time-to-first-render после дропа файла | ≤ 2 с |
| Начальный чанк лендинга (gzip), **без** Cesium и MapLibre | ≤ 250 КБ |
| Cesium и MapLibre — ленивые чанки, вне бюджета | обязательно |

> Бюджет считается **по маршрутам**, а не по всему бандлу: MapLibre сам по себе
> ~200–230 КБ gzip, и вместе с React+react-dom (~60 КБ) он один перекрывает
> лимит. Оба движка карт грузятся через `React.lazy` только на тех страницах,
> где реально нужны. В CI — проверка размера начального чанка, PR с превышением
> не проходит.

**Приёмы:**

- Один `Primitive` на трек вместо тысяч `Entity`.
- LOD: при отдалении камеры рисовать упрощённый трек (Дуглас–Пекер с динамическим ε).
- `requestRenderMode: true` — Cesium рендерит только при изменениях; критично для батареи ноутбука. Во время проигрывания включать непрерывный режим.
- Декодирование `.track` в Web Worker, передача `ArrayBuffer` через `transferable`.
- Виртуализация списка термиков и логбука.

## 8. Дизайн и UI

### 8.1. Принципы

1. **3D — герой экрана.** Интерфейс — плавающие стеклянные панели поверх сцены, а не рамка вокруг маленького вьюпорта.
2. **Тёмная тема по умолчанию.** Горы, небо и раскрашенные треки читаются на тёмном фоне лучше. Светлая тема — обязательна, но вторична.
3. **Прогрессивное раскрытие.** Новичок видит: трек, кнопку play, три цифры (макс. высота, дистанция, длительность). XC-пилот раскрывает панель аналитики.
4. **Никаких модалок поверх 3D.** Выдвижные панели сбоку/снизу, сцена продолжает жить.
5. **Ответственность за цвет.** Палитра вариометра — единственный «кричащий» элемент. Весь остальной UI — нейтральный, чтобы не спорить с ней.

## 10. API

REST, JSON, версионирование через путь `/api/v1`. Аутентификация — JWT в httpOnly cookie + refresh.

**Вход — только через OAuth-провайдеров, паролей нет** (решение владельца 26.09.2026,
задача 2.10): нет хэшей паролей, перебора, восстановления и писем. Сейчас — Google;
Apple — вместе с нативным приложением (Фаза 5).

- Access — JWT HS256 на 15 мин, cookie `skyline_at` на `/api/v1`.
- Refresh — случайные 256 бит на 30 дней, cookie `skyline_rt` только на `/api/v1/auth`;
  в БД (`sessions`) — лишь SHA-256. Ротация на каждый refresh; повтор уже сменённого
  токена позже 30 с — кража, гасятся все сессии пользователя; раньше — соседняя
  вкладка, ответ 409 «повтори».
- Google: authorization code + PKCE S256 + nonce, состояние входа — в подписанной
  cookie на 10 мин. Аккаунт создаётся или привязывается только по подтверждённому
  email; пользователь опознаётся по `sub`, не по email.
- Cookie — httpOnly, SameSite=Lax, Secure на https: фронт и API на одном origin.

DELETE /api/v1/users/{id}/follow

# Места
GET    /api/v1/sites?bbox&q&cursor&limit
GET    /api/v1/sites/{slug}
GET    /api/v1/sites/{slug}/flights?cursor&limit
POST   /api/v1/sites                      предложить новое место

# Сравнение
POST   /api/v1/comparisons                { flightIds: [...] }
GET    /api/v1/comparisons/{id}

# Видео (Фаза 4)
POST   /api/v1/flights/{id}/render        { preset, aspect, duration } → jobId
GET    /api/v1/renders/{jobId}            → { status, url? }
```

**Соглашения:**

- Все ошибки — RFC 9457 Problem Details (`application/problem+json`).
- Пагинация — курсорная (`?cursor=...&limit=...`), не offset.
- Rate limiting: загрузка — 20 файлов/час на пользователя, 5/час на IP для анонимов.
- Публичный доступ к `unlisted` полётам — только по `share_token` в пути: `/api/v1/public/flights/{shareToken}`.

### 11.4. Инфраструктура, хостинг и стоимость владения

#### Принцип: сервер не рендерит 3D

Прямое следствие выбора CesiumJS (§4.3) — визуализация исполняется в браузере пользователя. Сервер парсит файлы, считает аналитику и раздаёт байты. **GPU не нужен нигде, кроме сервиса рендера видео (Фаза 4).**

#### Расчёт нагрузки

Один полёт 4 часа / 14 400 точек:

| Шаг | Стоимость |
|---|---|
| Парсинг, чистка, производные | ~6–8 core-сек |
| Термики, глайды, ветер | ~3 core-сек |
| XC-скоринг FFVL/XContest | ~5 core-сек |
| **Итого** | **~15 core-сек** |

Оценка для Node; на C# было бы примерно вдвое меньше. 1000 полётов в день = 4,2 core-часа. **2 vCPU по-прежнему покрывают с запасом.**

Узкое место — не мощность, а спайки: FAI-скоринг до 120 с (§6.6) обязан идти отдельной очередью с ограничением параллелизма, иначе один патологический трек забивает воркер. И всё это — **в пуле `worker_threads`**: 15 секунд синхронного счёта в основном потоке остановят и очередь, и SSE.

**Хранилище:** сырой IGC в gzip ~150 КБ + `.track` ~95 КБ + превью WebP ~80 КБ ≈ **330 КБ на полёт**. 100 000 полётов = 33 ГБ.

**База:** упрощённая геометрия + агрегаты + термики ≈ 15–20 КБ на полёт. 100 000 полётов ≈ 2 ГБ, целиком в RAM. Именно ради этого точки не хранятся построчно (§5.3).

#### Конфигурации по фазам

| Фаза | Конфигурация |
|---|---|
| **0–1** | Один VPS 4 vCPU / 8 ГБ. Всё в docker-compose: API, воркер, Postgres, MinIO |
| **2–3** | Приложение + воркер 8 vCPU / 16 ГБ, Postgres отдельно, файлы → Cloudflare R2 (**нулевой egress** — критично, `.track` раздаётся на каждый просмотр расшаренной ссылки), CDN спереди |
| **4** | + GPU **по требованию**, не постоянный. Headless Chromium на программном рендере (SwiftShader) даст десятки минут на 900 кадров — неприемлемо. On-demand RTX-класс ≈ $0,35–0,40/час, ролик 30 с рендерится 2–3 мин ≈ **$0,02 за видео** |
| **6** | + хранение и раздача собственных terrain-тайлов (десятки–сотни ГБ) |

#### Стоимость владения

**Ключевое различие: CesiumJS (библиотека, Apache 2.0) бесплатна. Платим за ДАННЫЕ — рельеф и спутниковую подложку.** Это разные продукты разных вендоров.

| Поставщик данных | Цена | Включено |
|---|---|---|
| **Re:Earth Terrain + Esri/Sentinel-2** ✅ | **$0** | Выбор для старта, см. §4.4.1 |
| MapTiler Flex | $30/мес | 10 000 3D-сессий, 500k API-запросов; сверх — $6/1000 |
| Cesium ion Commercial | $149/мес | 5 000 imagery-сессий, 150 ГБ стриминга |

**Решение: Cesium ion не используется вовсе** — его Community-тариф запрещает коммерческое использование, а Commercial при нашем профиле нагрузки дороже MapTiler в разы. Стартуем на бесплатной связке; MapTiler — платный апгрейд при переходе порога из §4.4.1 (около 8–10 тысяч просмотров в месяц) либо если понадобится SLA.

Фаза 6 (собственный terrain на Copernicus) превращает регулярный платёж за сессии в разовую обработку + хранение. Это главный рычаг экономики на дистанции, а не только лицензионный вопрос.

**Регулярные расходы:**

| Статья | Стоимость | С какой фазы |
|---|---|---|

| Карты и рельеф | $0 → $30 → $60 | 1–2 |

**Разовые:** glTF-модель параплана — $0 (своя, из геометрии, `tools/make-paraglider.mjs`); Apple Developer $99/год и Google Play $25 — только при нативном приложении (PWA бесплатна). Шрифты (Inter, JetBrains Mono — OFL) и иконки (Lucide — MIT) бесплатны.

**Ориентир по фазам:** Фаза 0–1 ≈ €10/мес → Фаза 2–3 ≈ $75/мес → Фаза 4 ≈ $120/мес + GPU по факту → Фаза 6 ≈ $100/мес + комиссия биллинга.

#### Бесплатная конфигурация (выбрана для старта)

Целевая установка: **нулевые расходы сверх уже имеющихся VPS и домена** на Фазах 1–3. Достижимо полностью. Исходные условия: VPS с root-доступом, ≥ 4 ГБ RAM — стек из §4.2 помещается целиком, включая Postgres и MinIO.

| Статья | Бесплатное решение | Условия и лимиты |
|---|---|---|
| **Рельеф** | **Re:Earth Terrain** — `terrain.reearth.land`, quantized-mesh для CesiumJS | Без регистрации и API-ключа. Сервис MIT, данные Mapterhorn (NASADEM + Copernicus GLO-30) CC BY 4.0. Зум до 18. **Уже выполняет пересчёт геоид → эллипсоид** — снимает ловушку из §4.4. Best-effort, без SLA |
| **Спутниковая подложка** | **Esri World Imagery** через ArcGIS Location Platform (API-ключ), фолбэк — **Sentinel-2 cloudless (EOX)** | Esri: 2 млн тайлов/мес бесплатно, атрибуция «Powered by Esri». EOX: CC BY 4.0, без лимита, 10 м/пиксель, атрибуция `Sentinel-2 cloudless — https://s2maps.eu by EOX IT Services GmbH (Contains modified Copernicus Sentinel data)`. Выбор между ними — по §4.4.1 |
| **БД** | Postgres 17 + PostGIS в Docker на своём VPS | — |
| **Объектное хранилище** | Cloudflare R2 free | 10 ГБ, 1 млн Class A и 10 млн Class B операций/мес, **нулевой egress** |
| **CDN** | Cloudflare free plan | Безлимитный трафик |
| **Транзакционная почта** | Resend free | 3 000 писем/мес |
| **Мониторинг** | Sentry free | 5 000 событий/мес |
| **CI** | GitHub Actions | 2 000 мин/мес для приватных репозиториев |
| **XC-скоринг** | `igc-xc-score`, open source | — |
| **Экспорт видео** | Клиентский MediaRecorder (§7.6) | Рендерит машина пользователя — бесплатно всегда |
| **Шрифты, иконки** | Inter, JetBrains Mono (OFL), Lucide (MIT) | — |

**Ёмкость бесплатного хранилища.** При хранении сырого IGC в gzip (текст жмётся в 5–6 раз) и превью в WebP выходит ≈ 330 КБ на полёт → **~30 000 полётов** в лимит 10 ГБ. Рекомендуемое разделение: `.track` и превью (читаются на каждый просмотр, выигрывают от нулевого egress) — в R2; холодные сырые файлы — на диске VPS.

**Что осознанно приносится в жертву:**

1. **Резкость подложки у земли — при условии, что выбран Sentinel-2.** 10 м/пиксель против ~0,3–1 м. При типичной высоте полёта 1000–3000 м камера далеко от рельефа и разница почти не читается; мыло заметно вблизи старта и посадки. Бесплатный лимит Esri (§4.4.1) снимает этот компромисс на первом году — если разрешение Esri над целевыми районами окажется действительно выше.
2. **Серверный рендер видео отсутствует** — только клиентский экспорт.
3. **Нет SLA на тайлы.** Re:Earth и EOX — добровольные публичные сервисы: best-effort, возможны rate-limit'ы при доминировании одного клиента.

> **Следствие для Фазы 6.** Собственный terrain-пайплайн перестаёт быть способом сэкономить и становится вопросом **надёжности и независимости** — переезжать нужно тогда, когда падение чужого бесплатного сервиса станет неприемлемым, а не когда счёт вырастет. Это усиливает требование из §4.4: `ITerrainProvider` и `IImageryProvider` за интерфейсами, смена поставщика — изменение конфигурации, а не кода.

> **Условие перехода на платные тарифы:** появление платной подписки (Фаза 6), либо жалобы пользователей на резкость подложки, либо rate-limit от публичных тайл-сервисов. До наступления любого из трёх — платить не за что.

#### Юридические ограничения на размещение

> ⚠️ **Локализация персональных данных (РК).** Закон РК «О персональных данных и их защите» №94-V требует, чтобы базы, содержащие персданные граждан Казахстана, физически находились на территории РК. Санкции — штрафы и блокировка сайта операторами связи.
>
> **Архитектурное следствие, которое надо заложить сразу:** разделить хранение так, чтобы `users` и всё персонально идентифицирующее могло жить в казахстанском ДЦ отдельно от треков, `.track`-файлов и превью. Позже разносить дорого.
>
> Латентность Алматы → Франкфурт ~90–120 мс; с CDN спереди это приемлемо, поэтому географию диктует закон, а не скорость.
>
> Формулировки закона имеют нюансы (есть исключения при явном согласии субъекта на трансграничную передачу) — требуется консультация юриста до выбора площадки. Оператором выступает ТОО.

> ⚠️ **Приём платежей (Фаза 6).** Stripe не поддерживает Казахстан. Требуется merchant of record (Paddle, Polar, Lemon Squeezy и аналоги) с комиссией порядка 5% + фикс против 2,9% у Stripe. Заложить в юнит-экономику подписки **до** проектирования тарифов, а не после.

### 11.5. Наблюдаемость

- Структурные логи (pino → JSON), корреляция по `flightId`.
- OpenTelemetry traces на конвейере обработки — видеть, какой шаг тормозит.
- Метрики: время каждого шага конвейера, доля неудачных парсингов по формату и по модели прибора (это подскажет, чей формат чинить).
- Sentry на фронте: обязательно ловить WebGL context lost и падения Cesium.

### 11.6. Поддержка браузеров

Chrome/Edge 120+, Safari 17+, Firefox 120+. WebGL2 обязателен для 3D.

**Деградация без WebGL2** — важно, что она не может быть «на MapLibre»: MapLibre GL JS сам требует WebGL (в v6 WebGL2 объявлен обязательным). Настоящий фолбэк — растровый: Leaflet + статичные тайлы OSM с треком как SVG-полилинией, плюс график высоты и вся текстовая аналитика (термики, ветер, XC). Как дополнительная опция — серверный PNG-рендер 3D-сцены через `apps/render` (Фаза 4): пользователь без WebGL получает хотя бы статичную красивую картинку полёта.

### Фаза 4 — Кинематика и видео (≈2–3 недели)

**Цель:** US-09. Главный виральный механизм.

```

4.2  Сглаженные переходы камеры (Безье + кастомный easing)

**DoD:** пилот за два клика получает 15-секундное вертикальное видео своего полёта в качестве 1080×1920, годное для Instagram Reels.

### Фаза 5 — Мобильное приложение (≈3–4 недели)

```
5.1  PWA: манифест, service worker, offline-логбук, установка на домашний экран
5.2  Web Share Target API: XCTrack «поделиться .igc» → сразу в приложение
5.3  Адаптив просмотрщика: bottom-sheet, жесты, оптимизация 3D под мобильный GPU
     (упрощённый terrain, отключение curtain wall по умолчанию)
5.4  Push-уведомления (комментарии, готовность рендера)
5.5  Оценка спроса → решение по нативному React Native приложению:
     основной аргумент «за» — прямой доступ к файловой системе прибора
     по USB/Bluetooth и фоновая синхронизация
```

**Дальше — собственный полётный прибор, по шагам от безопасного к рискованному.**
Решение владельца 26.09.2026. Ниша: на iPhone нет XCTrack, FlySkyHy платный;
свой прибор даёт цельный путь «взлетел → сел → полёт уже в Skyline» и повод
открывать приложение на каждый полёт — основу будущего суперапа для пилота.

```
5.6  Нативное приложение (React Native) с режимом «Полёт»: только запись трека
     (IGC) и live-трекинг для друзей и спасателей, онлайн-просмотр в 3D.
     Риск низкий: сбой приложения не лишает пилота прибора — он летит
     со своим, как обычно
5.7  Варио-звук: нативный модуль под iOS и Android (фильтр Калмана
     барометр + акселерометр, задержка звука < 100 мс). Кроссплатформенный
     слой для этого не годится. Целевая аудитория — начинающие без прибора
5.8  Навигация: маршрут по точкам, глайд до цели, предупреждения
     о воздушном пространстве, задания соревнований — только если
     5.6–5.7 набрали пользователей
```

Ограничения, которые нельзя упускать:

- **Прибор — вопрос безопасности.** Зависание, севшая батарея или перегрев
  в воздухе оставляют пилота без прибора. Каждый шаг — месяцы тестов
  в реальных полётах до публичного релиза.
- **Признание треков.** Чтобы XContest и соревнования принимали треки,
  нужна подпись IGC (G-запись) и допуск. Без этого кроссовики не перейдут.
- **Не заменять, а интегрироваться** там, где пилоты уже привыкли к своим
  инструментам: XCTrack, Flymaster, Syride — импорт и «поделиться» остаются
  первым путём в Skyline.

## 13. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Разнобой IGC-диалектов у приборов | Высокая | Средн. | Большой набор fixtures с реальных приборов; метрика «доля неудачных парсингов по модели»; ручной разбор топ-ошибок |
| **Блокировка event loop тяжёлым счётом** | **Высокая** | **Высок.** | Специфичный для Node риск. Всё CPU-тяжёлое — только в `worker_threads` (§5.2). Проверка: при обработке 4-часового трека `/health` отвечает быстрее 200 мс. Вынести в тест |
| **Лицензия Cesium ion блокирует монетизацию** | **Высокая** | **Высок.** | Community-тариф запрещает коммерческое использование. `ITerrainProvider` за интерфейсом с первого дня; миграцию на собственный Copernicus-пайплайн запланировать **до** запуска платной подписки, а не в Фазе 6 «когда-нибудь» |
| Ошибка геоид/эллипсоид в собственном terrain | Средняя | Высок. | Приёмочный тест: известная точка с измеренной высотой — расхождение рельефа и GPS-высоты на земле < 5 м |
| Производительность 3D на слабых машинах | Средняя | Высок. | Жёсткие требования §7.7 с первого дня; тест на встроенной графике при каждом релизе; graceful degradation в 2D |
| Термики детектятся неверно | Средняя | Высок. | Ручная разметка 20 треков как «золотой стандарт»; регрессионные тесты на точность детекции |
| Серверный рендер видео дорог | Высокая | Средн. | Только в платной подписке; клиентский рендер — бесплатно |
| Юридические претензии по воздушному пространству | Низкая | Высок. | Явный дисклеймер; данные только справочные; не позиционировать как навигационный инструмент |
| Ниша слишком мала для окупаемости | Средняя | Высок. | Фаза 1 — быстрый запуск и замер спроса до больших вложений; выход за пределы парапланов (дельтапланы, планеры, спидрайдинг) почти не требует доработок |

## 14. Конвенции для Claude Code

Содержимое `CLAUDE.md` в корне репозитория — см. отдельный файл. Ключевое:

```
1. Никогда не менять формат .track без поднятия version в заголовке
   и обновления round-trip тестов в packages/track-format.
2. Любой новый алгоритм анализа = новый модуль в packages/analysis
   + тест на fixtures. Без теста PR не принимается.
3. Cesium-код изолирован в apps/web/src/viewer/. Остальное приложение не знает
   про Cesium. Импорт Cesium вне этой папки — ошибка линтера.
4. Никаких магических чисел в алгоритмах. Все пороги (радиус круга, минимальная
   скороподъёмность и т.д.) — в packages/core/constants.ts с комментарием,
   почему именно такое значение.
5. Единицы измерения: внутри системы ВСЕГДА СИ (метры, м/с, секунды, градусы).
   Конвертация — только на границе UI.
6. Время внутри системы — всегда UTC. Локальное время — только для отображения.
7. Строки UI — только через i18n, никакого хардкода.
8. Все API-ответы — через Zod-схемы из packages/core, никогда не отдавать
   строку БД напрямую.
9. CPU-тяжёлое — только в worker_threads. Синхронный код дольше ~100 мс
   в основном потоке недопустим.
10. packages/core не зависит ни от чего. Проверяется линтером.
```

**Рекомендуемый порядок работы с Claude Code:**

1. Начинать каждую фазу с `/plan` по соответствующему разделу этого ТЗ.
2. Одна задача из списка фазы = одна сессия = один PR. Не смешивать.
3. Перед задачами на алгоритмы — сначала написать тест с ожидаемыми значениями, потом реализацию (Claude Code хорошо работает от теста).
4. Fixtures добавлять по мере нахождения проблемных файлов — они накапливаются и становятся регрессионным набором.
5. Для задач по 3D — просить скриншот/GIF результата, визуальную регрессию текстом не проверить.

## 15. Открытые вопросы к владельцу продукта

1. **Название и домен.** Есть ли предпочтения? Проверить свободность `.com` и `.kz`.
2. **География запуска.** Казахстан/СНГ сначала, или сразу международно? Влияет на приоритет локализации, выбор мест старта для сидинга и на источник рельефа (для Тянь-Шаня качество открытых DEM нужно проверить отдельно).
3. **Монетизация.** ✅ Решено 26.09.2026: пока всё бесплатно, монетизация — позже, по обстоятельствам. Биллинг и тарифные планы заранее не закладываются.
4. **Дельтапланы/планеры/спидрайдинг.** Включать сразу? Почти не требует доработок, но меняет позиционирование и подбор алгоритмов (у планеров другие скорости и радиусы виражей — пороги детекции надо параметризовать по типу ЛА).
5. **Сообщество как приоритет.** Соцчасть (Фаза 3) — это большой объём работы. Готов ли ты модерировать контент, или лучше ограничиться приватным шарингом по ссылке?
6. **Юрлицо.** Проект под ТОО (JATE) или отдельная сущность? Влияет на биллинг и лицензионные договоры с поставщиками данных.
